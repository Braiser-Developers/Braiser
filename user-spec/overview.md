# Braiser 总览

## 项目定位

Braiser 是作者开发的简易 MCP 工具，为 Agent 提供更轻量级的浏览器操作能力。

## 设计初衷

Braiser 的设计初衷是提供一种轻量的网页操作方式：舍弃 GUI 信息和复杂的属性信息，只返回精简的网页 DOM 结构。它以舍弃一部分能力为代价，换取比 computer use 或通用浏览器插件更少的 token 消耗，以及更简单的操作（不使用 JS 或 CDP）。（2026-11-13）

「不使用 JS 或 CDP」指 Agent 不需要写 JS、不需要调用 CDP，只用 Braiser 提供的固定动作；Braiser 内部可以使用 CDP（见 [D-0012](decisions/0012-internal-cdp.md)）。

现阶段舍弃截图。作者是在看到实测数据（一张截图的 token 比整页文本少得多，见 [浏览器快照 token 实测](../references/browser-snapshot-tokens-2026-11-13.md)）之后，确认现阶段仍不提供截图的。（2026-11-13）

## 使用场景

作者把需求分成两类：

1. 在作者不熟悉的网站上完成一件特定的事，例如注册一个 access token、修改一项配置。目的是让 Agent 替作者省去不必要的探索。
2. 类似的需求会经常出现，例如定期去教学网上下载作业、操作 GitHub。作者之前想过，这类需求大概会结合 Playwright 脚本做自动化。

现阶段主要考虑第一类。（2026-11-13）

## observe 改版

作者想讨论 observe 大改的事。目前已确认：现阶段不做按关键词查找元素；把快照存成文件、让 Agent 自己查的做法暂时不考虑，以后再说。（2026-11-13）

页面快照和动作结果的需求不同（作者 2026-11-13 提出）：

- **页面快照**：重要的是给出页面的信息。从需求上讲需要的信息量很大，所以文字、结构等都要保留。
- **动作之后的返回**：需求上往往不需要很多信息，甚至只需要"是否成功"这 1 bit，所以返回的东西可以精简很多。比如只返回可交互元素发生的变化，省去文字之类的信息，因为那些并不重要，只需要看出一个大变化。

页面元素的识别（是什么、叫什么、什么状态、是否可见）照搬 Playwright 的逻辑，输出给 Agent 的格式由 Braiser 自己做，作者同意先试试（见 [D-0013](decisions/0013-playwright-recognition-layer.md)）。动作后的返回做法见 [D-0014](decisions/0014-lean-action-result.md)。

## 项目背景

Braiser 是作者大约一年前做的，作者觉得当时做得比较粗糙（原话：「当时做的比较垃圾」）。现在作者调整了定位，打算接着用；现有实现可能需要调整，作者想先弄清现状再决定怎么改。（2026-11-13）

## 当前远程访问需求

作者希望远程 Linux 服务器中的 Agent 能通过 Braiser MCP 操作作者本机的浏览器。本机已经可以通过 SSH 连接这台服务器。

当前先支持浏览、点击、填写和读取页面内容即可。

以上预期依据作者在 2026-11-12 的需求说明和范围确认整理。

当前目标环境与连接方案见 [D-0002](decisions/0002-remote-access.md)，统一启动入口见 [D-0004](decisions/0004-foreground-ssh-launcher.md)。
