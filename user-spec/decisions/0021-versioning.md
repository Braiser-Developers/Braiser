# D-0021 统一版本号，各部分报告构建号并提示未更新的部分

- 状态：有效
- 日期：2026-11-14
- 决策者：讨论
- 服务于：
  - 作者预期：作者要做一次版本号更新，同意 agent 的建议（2026-11-14）
  - 上游决策：[D-0015](0015-extension-bundling-and-e2e.md)、[D-0018](0018-remote-tunnel-switch.md)

## 背景

版本号写在根 `package.json`、`mcp/package.json`、扩展 `manifest.json` 和 MCP 服务启动代码四处，都是 0.1.0，仓库里已有 2026-07-17 的 `v0.1.0` 标签。这几天多次出现某一部分停在旧代码上的情况：扩展重新构建了但没重新加载、daemon 是旧进程、服务器副本没同步，每次都要靠报错才发现。作者同意：这次版本号用 0.2.0，扩展、MCP、daemon 统一一个版本号，各部分报告版本、对不上就提醒。作者认为不需要单独的 CHANGELOG，决策记录已经足够；agent 同意，建议版本说明写在标签信息里。

## 决策

- **版本号**：只在根 `package.json` 里改。`npm version <新版本>` 会运行 `scripts/sync-version.mjs`，把版本同步到另外两个文件（只替换版本值，不改其余格式）；MCP 服务从构建信息里读取版本。测试检查三处一致。版本号用"大.中.小"三段，0.x 期间加功能或改用法升中间一位，只修 bug 升最后一位。
- **构建号**：构建时用 `scripts/build-info.mjs` 对各部分的源码算哈希，取前 12 位，写进 `mcp/dist/build-info.json` 和 `extension/dist/build-info.json`；扩展的构建号同时编译进代码。同一份源码在任何机器上算出的构建号都相同，源码不变就不变，所以只多跑一次构建不会被误报。
- **运行中的版本**：MCP 和 daemon 在启动时读一次自己的构建号；daemon 在扩展连上时请它报告编译进去的版本和构建号（旧扩展答不上来，记为"太旧"）。`daemon.status` 附带 `versions`：daemon 和扩展正在运行的构建，以及浏览器主机磁盘上最新的构建。
- **提示**：`braiser.status` 和 `npm run remote -- status` 比较这些信息，给出具体的提示：扩展需要重新加载、daemon 需要重启、这个会话的 MCP 需要重开，或者（远程模式下）服务器副本和浏览器主机的代码不一致、需要同步。
- **发布**：打带说明的标签（如 `v0.2.0`），说明里写一两句这一版的主要变化。不维护 CHANGELOG 文件。`protocolVersion` 仍只表示 daemon 与 MCP 之间通信格式的版本，与发布版本号无关。

## 考虑过、没有采用

- 只比较版本号：开发中同一版本会构建很多次，发现不了"重新构建了但没重新加载"。
- 用构建时间或提交号作构建号：每次构建都会变，或者未提交的改动看不出来，会误报或漏报。
- 各部分分开编号：只有作者一人维护，分开编号只会更乱。
- CHANGELOG 文件：目前只有作者在用，决策记录加提交历史已经够用。

## 代价

- 第一次升级时要重新加载一次扩展，之后才能自动发现扩展没重新加载。
- 构建号只覆盖各自目录的源码；改了依赖版本但源码没变时，构建号不变。

## 什么时候应该重新考虑

有别人开始使用 Braiser、需要面向使用者的更新说明时，再考虑 CHANGELOG；需要分部分独立发布时，再考虑分开编号。
