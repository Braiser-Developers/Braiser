# 决策

一条决策记录：为了满足哪些作者预期，选择了怎样的做法，为什么。规则见 [../README.md](../README.md)。

## 约定

- 编号 `D-NNNN`；一条决策一个文件：`NNNN-简短英文标识.md`；编号四位、递增、永不复用。项目分成几个部分时，各部分的决策放在自己的 `user-spec/decisions/`，编号用自己的前缀（见 [../README.md](../README.md)「一条内容放哪」）。
- **引用写法**：`D-0001`，链接到对应文件。
- **状态**：`有效` / `有效（未实现）` / `已取代（→ D-xxxx）` / `部分被取代（→ D-xxxx）：说明哪部分` / `已废弃`。决策文件不删除；被取代时，旧决策标注取代者，新决策标注取代了谁。
- **修改还是新建**：
  - **推翻决策**（换了方案、方向反转——按旧版本做会做出不同的东西）→ **新建决策**取代旧的；
  - **小的修改**（补充细节、修措辞、更新状态、统一用词、补引用），或**修改刚定下的决策**（尚在打磨、还没实现）→ **原位修改**；
  - 原位修改不必写变更记录（git 历史可以看到）；但如果这次修改有**非平凡的理由**，在决策末尾的「修订记录」里写明改了什么、为什么。
- **修 bug**：每修一个 bug，都**新建一条决策**，写上「修复的 bug」一节；如果 bug 出在某条已有决策的做法上，新决策标注取代了它的哪一部分。
- **决策者**：`作者` / `讨论`（作者与 agent 讨论后确定）/ `agent`（agent 基于作者需求自行决定，作者不一定看过）。
- 决策可以引用上游决策。

## 模板

```markdown
# D-NNNN 标题（一句话说清楚决定了什么）

- 状态：有效
- 日期：YYYY-MM-DD
- 决策者：作者 / 讨论 / agent
- 服务于：
  - 作者预期：[xxx.md「某一节」](../xxx.md)
  - 上游决策：D-xxxx

## 背景
面对什么问题，有哪些约束。

## 决策
决定怎么做。

## 考虑过、没有采用
- 方案 A：为什么没选。

## 代价
接受了哪些缺点。

## 什么时候应该重新考虑
出现哪些情况时，这条决策值得推翻。

## 修复的 bug（修 bug 时必写）
- 现象：作者看到了什么，怎样复现；
- 原因：bug 是怎么产生的；
- 为什么原来的做法会出 bug：重构时**不能**再采用的做法；
- 怎么验证修好了：哪条测试或检查会在 bug 回来时失败。

## 修订记录（可选）
- YYYY-MM-DD：改了什么；为什么。
```

「考虑过、没有采用」「代价」「什么时候应该重新考虑」可以在确实没有内容时省略，但应尽量写——它们是将来推翻决策时最有用的信息。「修复的 bug」在修 bug 的决策里必写。「修订记录」只在原位修改有非平凡理由时才写。

## 鼓励推翻决策

**在符合作者预期的前提下，我们鼓励决策被推翻。** 因此要如实记录一条决策有多「硬」，不要把随手的选择写得像深思熟虑：

- 没有强烈理由、只是随便选了一种方案（agent 自己定的尤其常见）→「什么时候应该重新考虑」写 **随时可以**；
- agent 问作者、作者选了某个选项但没说原因 → 理由写 **作者没说原因**；
- 作者表达了「随便，就选方案 A」→ 理由写 **作者没有强烈的原因**，「什么时候应该重新考虑」写 **随时可以**。

只有真正有支撑的决策，才写具体的重新考虑条件。
