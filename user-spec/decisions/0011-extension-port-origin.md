# D-0011 扩展端口只接受 Chrome 扩展来源的连接

- 状态：有效
- 日期：2026-11-13
- 决策者：讨论
- 服务于：
  - 作者预期：[overview.md](../overview.md)
  - 上游决策：[D-0003](0003-credentials-and-tools.md)、[D-0005](0005-extension-replacement.md)

## 背景

daemon 在 127.0.0.1:17832 等待扩展 Bridge 页面连接。D-0003 给客户端端口 17833 加了 token，并拒绝带 Origin 的浏览器连接，但扩展端口没有任何校验。D-0005 又规定新连上的扩展会顶替旧连接。两者叠加，任何能连到本机回环地址的东西都能冒充扩展。agent 指出这个问题并提出只接受扩展来源的修法，作者回复"可以"（2026-11-13）。

## 决策

扩展端口在 WebSocket 握手时检查 Origin，只接受 `chrome-extension://<32 位扩展 ID>`，其他来源和没有 Origin 的连接一律返回 403，不进入顶替流程。扩展代码不变：Bridge 是扩展页面，浏览器会自动带上扩展来源。

## 考虑过、没有采用

- 固定某一个扩展 ID：扩展以"加载已解压"方式安装，ID 随目录变化，需要额外配置；当前只需挡住网页。
- 给扩展也发 token（扩展配对）：需要扩展侧存储凭据和配对流程，改动大；挡住网页不需要这一步。

## 代价

- 其他已安装的 Chrome 扩展仍可冒充 Braiser 扩展。
- 本机非浏览器进程可以伪造 Origin 头。同一用户的进程本来就能读取 `~/.braiser` 的 token，不在这条决策的防护范围内。

## 什么时候应该重新考虑

需要防范其他扩展、多用户共用一台机器，或者扩展端口不再只在回环地址监听时，改为扩展配对或固定扩展 ID。

## 修复的 bug

- 现象：本机任何进程（推断也包括浏览器中的网页，未实测）连上 17832 后，daemon 会把它当成扩展，并断开真正的 Bridge。冒充者能收到 Agent 发出的请求（例如要填进页面的文字），还能返回伪造的页面内容；真正的 Bridge 约 1.5 秒后重连，两边来回顶替。
- 原因：扩展端口的 WebSocketServer 没有 verifyClient，D-0005 的顶替逻辑对所有连接一视同仁。
- 为什么原来的做法会出 bug：回环地址不是身份。网页可以向 127.0.0.1 发起 WebSocket，本机其他进程也可以；"最新连接就是扩展"只有在连接方身份可信时才成立。重构时不能去掉扩展端口的来源校验，也不能让未通过校验的连接触发顶替。
- 怎么验证修好了：测试 `extension port rejects web pages and non-extension clients without replacing the bridge` 用网页来源、`null`、错误长度的扩展来源和无 Origin 四种连接，断言都得到 403，且真正的扩展仍能响应请求；去掉校验后该测试会失败。2026-11-13 在作者本机重启 daemon 后实测：真实 Bridge 重新连上，`https://example.com` 来源和无 Origin 连接都得到 403，扩展连接不受影响。
